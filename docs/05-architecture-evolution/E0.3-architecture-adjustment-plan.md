# E0.3 — Architecture Consolidation & Engineering Readiness

**Baseline:** E0.2.2.3 documentation/design baseline  
**Status:** Proposed — pending architecture review  
**Implementation:** Not Implemented  
**Verification:** Not Verified  
**Target branch:** docs/e0.3-architecture-consolidation

## 1. Purpose

E0.3 converts the E0.2 product and architecture baseline into an implementation-ready engineering contract. It is a controlled refinement, not a product reset. The eight existing business domains, Local-first strategy, Modular Monolith, Tauri 2 + Rust + React, and single local SQLite topology remain the baseline unless a separately accepted ADR supersedes them.

Documentation completion does not imply software implementation or runtime acceptance.

## 2. Decisions retained

The following accepted decisions remain unchanged:

- ADR-002: Modular Monolith through the initial desktop product.
- ADR-003: Local-first ownership; external knowledge systems retain authority over canonical content.
- ADR-004: provider-neutral Agent Adapter boundary and centralized authorization.
- ADR-005: offline-first core runtime.
- ADR-006: one authoritative local app.sqlite for Alpha 0.1 through V1.0, with backend-enforced Workspace isolation.
- ADR-013–016: Learning & Growth as a first-class domain, explicit Project integration, evidence-based user-confirmed assessment, and separate Learning/Knowledge ownership.

No microservices, mandatory server, mandatory PostgreSQL, shared writable network SQLite, autonomous high-risk execution, or automatic skill scoring are introduced by E0.3.

## 3. Architecture adjustments

### 3.1 Coordination Layer (logical, not a new business domain)

Formalize a cross-cutting application coordination capability responsible for:

- Cross-domain use-case orchestration through published commands and query DTOs.
- Correlation and causation context propagation.
- Durable operation tracking for long-running local and external work.
- Central authorization and approval enforcement before protected side effects.
- Transactional Outbox recording and idempotent event consumption.
- Retry classification, cancellation, reconciliation, and recovery.
- Consistent audit outcomes and actionable error mapping.

It does not own business entities belonging to the eight domains, expose private repositories, act as a generic service locator, or permit direct cross-domain repository access. It remains inside the modular monolith.

### 3.2 Enforceable Rust module boundaries

Retain a Rust workspace, but do not create one crate per business domain before boundaries are exercised. Start with a small set:

- paw-domain: domain entities, value objects, invariants, and domain contracts; no infrastructure dependency.
- paw-application: use cases, published ports, DTOs, authorization orchestration, and coordination.
- paw-infrastructure: SQLite, filesystem, OS credential-store, logging, and adapter implementations.
- paw-desktop: Tauri commands/events and application composition root.

Business domains initially remain explicit modules with private internals. Extract a domain crate only when ownership, dependency direction, test isolation, or parallel development gives a demonstrated benefit.

Dependencies point inward. UI must not access SQLite or invoke external tools directly. Domain must not depend on Tauri, SQL drivers, OS APIs, or provider SDKs. One domain must not import another domain's private repository or persistence model.

### 3.3 Operation lifecycle and reliability

Keep business Task, Workflow Run, external Agent Execution, and cross-cutting Operation as distinct concepts with separate owners and state machines. Connect them through stable IDs and correlation metadata.

Long-running operations persist operation ID, kind, owner, workspace, status, timestamps, correlation ID, attempt information, and safe diagnostic outcome. Persisted progress is authoritative; UI progress is a projection.

External calls must not occur inside long-lived SQLite transactions. Record local intent and Outbox messages atomically where downstream delivery is required. Delivery is at-least-once; consumers are idempotent. Treat timeout after possible submission as indeterminate, reconcile before retry, and never claim exactly-once behavior without provider evidence.

### 3.4 Version cross-domain contracts

Standardize identifiers, command/query DTOs, event envelopes, schema versioning, idempotency, and deprecation. Events are minimal, workspace-scoped, versioned, and contain no secrets or full document bodies. Consumers handle duplicate delivery and unknown future fields safely. Incompatible changes require a new contract/event version and an explicit migration/deprecation plan.

### 3.5 Workspace security boundary

Workspace is a backend-enforced data isolation boundary, not merely a UI filter. Every workspace-scoped record, relationship, query, search, import, background operation, attachment access, Agent request, export, and backup path must be scoped and authorized. Cross-workspace references are denied by default. UI selection and file-picker selection do not create persistent grants.

### 3.6 User-facing information architecture

Use task-oriented navigation:

- Home: cross-domain read-only overview and attention items.
- My Work: goals, areas, projects, tasks and personal queues.
- Learning: roadmaps, plans, sessions, skills and evidence.
- Knowledge: local notes, references and source availability.
- Agents: providers, capabilities, approvals and execution history.
- Creator: ideas, drafts, review and publication records.
- Automation: workflow definitions, runs and approvals.
- Settings: Workspace, integrations, security, backup and diagnostics.

Engineering is primarily surfaced through Project/Artifact context in the first release. Dashboard remains a composition read model, never an authoritative domain.

## 4. Delivery scope

| Stage | Scope | Exit evidence |
|---|---|---|
| E0.3 | Review and accept architecture refinements; reconcile docs | ADR review, consistent contracts, no unresolved P0 design conflict |
| E1 | Tauri/Rust/React skeleton, Workspace context, SQLite initialization and migration | Windows native build; create/reopen Workspace; persistence and dependency tests |
| E2 | Goal/Area/Project/Task vertical slice; scoped search and attachments | Offline CRUD/search, scope-denial tests, restart persistence |
| E3 | Backup/restore, audit, operation primitives and Outbox | Restore drill, interrupted migration and operation recovery tests |
| E4 | Knowledge references and basic Learning lifecycle | Cross-domain contract tests |
| E5 | Agent adapter and mediated authorization | Fake-provider conformance, approval binding, unknown-outcome reconciliation |
| E6+ | Evidence/assessment, Creator and Automation increments | Domain-specific acceptance evidence |

Alpha 0.1 remains intentionally narrow: local Work Management and the minimum platform/data reliability required to trust it. E0.3 does not pull complete Learning, Creator, Automation, or multi-Agent orchestration into Alpha 0.1.

## 5. Review gates

### P0 — required before E1 expands

- [ ] Coordination responsibilities and ownership accepted.
- [ ] Rust dependency direction and initial crate/module boundary accepted.
- [ ] Workspace scoping specified for all read/write/background paths.
- [ ] Operation, Workflow Run, Task and Agent Execution remain distinct.
- [ ] Outbox/idempotency/retry/unknown-outcome semantics specified.
- [ ] Cross-domain contract versioning and compatibility rules accepted.
- [ ] Alpha 0.1 scope and E1 vertical-slice acceptance explicit.

### P1 — required before corresponding feature delivery

- [ ] UI navigation and information architecture reviewed.
- [ ] Attachment content addressing and retention decision supported by prototype evidence.
- [ ] Representative SQLite performance baseline established.
- [ ] Plugin packaging/distribution model evaluated.
- [ ] Multi-device synchronization remains out of scope until separately designed.

## 6. Non-goals

E0.3 does not authorize microservices, server-side runtime, PostgreSQL as a desktop dependency, database-per-Workspace, shared network database access, a generic plugin marketplace, arbitrary shell access, autonomous publication, automatic skill scoring, or full multi-Agent orchestration.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Coordination becomes a god service | Keep business invariants in owning domains; expose named use cases |
| Too many Rust crates increase solo-developer overhead | Start with a few crates; extract only against demonstrated need |
| Operation duplicates Task/Workflow/Agent state | Define distinct owners and link by IDs |
| Event versioning becomes ceremonial | Add compatibility tests and migration examples |
| Workspace isolation is bypassed by secondary paths | Test queries, jobs, search, attachments, imports/exports and adapters |
| E0.3 expands MVP | Keep Alpha 0.1 restricted to Work Management vertical slice |

## 8. Definition of done

E0.3 may be marked Accepted only after ADR-017–020 are reviewed and status-updated; README, ADR index, roadmap, system/application/data architecture, authorization model, and cross-domain contracts are consistent; accepted ADRs remain consistent; requirement traceability and documentation validation pass; and E1 acceptance cases are recorded.
